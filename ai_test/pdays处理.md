这三个字段的核心难点在于：**它们记录的是“上一次营销活动”的信息，但现实中很多客户是“第一次被营销”，导致这三列在逻辑上高度绑定，又充斥着业务默认值。**

用直白的生活场景来拆解这三列背后的业务逻辑与工程处理思路。

---

### 一、这三列分别代表什么？

| 字段 | 含义 | 第一次接触的新客户（默认值） | 老客户（之前联系过） |
| --- | --- | --- | --- |
| `pdays` | 距上次营销联系的天数 | `-1`（表示压根没联系过） | 比如 `90`（90 天前联系过）、`0`（当天联系过） |
| `previous` | 本次营销前的历史联系次数 | `0` 次 | 比如 `1` 次、`3` 次 |
| `poutcome` | 上次营销的结果 | `'unknown'`（无历史结果） | `'success'`、`'failure'`、`'other'` |

理想情况下，一个**纯新客户**的这三列必须是固定的组合：

> `pdays == -1` 且 `previous == 0` 且 `poutcome == 'unknown'`

---

### 二、为什么要特意拆开 `pdays`？

这是许多人在做这个数据集时最容易掉进去的坑：**把 `-1` 当作普通数字直接扔给模型。**

#### 1. 为什么直接用 `-1` 会误导模型？

* 在线性模型或神经网络中，`-1`、`0`、`10`、`100` 会被当成一条连续的数轴。
* 现实中：
* `pdays = 0` 表示 **“今天刚联系过”**（客户意向非常热乎）。
* `pdays = 300` 表示 **“将近一年前联系过”**（关系已冷却）。
* `pdays = -1` 表示 **“从未联系过”**。


* 如果直接输入 `-1`，模型会以为 `-1` 比 `0` 还小，甚至推导出“`-1` 天比 `0` 天还更接近今天”，这在业务含义上完全是错位的。

#### 2. 怎么解决？——拆成“开关”和“尺子”

为了让模型既理解“有没有历史”，又理解“隔了多久”，我们需要把它拆成两个维度：

1. **开关（`has_previous_contact`）**：
* `0` = 没联系过（新客）
* `1` = 联系过（老客）


2. **尺子（`contact_gap`）**：
* 如果没联系过，把 `-1` 重置为 `0`；如果联系过，保留原本的天数。



```
原始数据：
pdays:   -1  |  0  |  15  |  90

拆分之后：
has_previous_contact:   0  |  1  |   1  |   1   (告诉模型：谁是老客)
contact_gap:            0  |  0  |  15  |  90   (告诉模型：老客隔了多久)

```

> **模型如何理解这两个特征？**
> * 看到 `has_previous_contact = 0` 且 `contact_gap = 0`：这是纯新客户，不要按历史衰减规律去评估。
> * 看到 `has_previous_contact = 1` 且 `contact_gap = 0`：这是今天刚联系过的活跃老客，重点跟进！
> 
> 

---

### 三、那 21 行“逻辑打架”的数据是怎么回事？

在真实业务系统里，经常会出现录入脏数据。前面提到的 21 行冲突，其实是这三列**自相矛盾**了：

* **矛盾情况 A**：`pdays == -1`（说自己从未联系过），但 `previous = 2`（历史联系了 2 次）或者 `poutcome = 'failure'`（记录了上次失败）。
* **矛盾情况 B**：`pdays == 180`（说半年前联系过），但 `previous = 0`（历史联系次数写着 0）。

#### 为什么不能随便改？

很多初学者第一反应是：“既然 `pdays == -1`，那我就强行把 `previous` 改成 0，把 `poutcome` 改成 unknown 吧”。

**这样做很危险，因为你不知道哪一列是真实的：**

* 可能是业务员忘了把 `-1` 改掉，实际上客户上个月才办过业务失败了？（此时改掉 `poutcome` 会丢失宝贵的失败记录）
* 还是说这真的是个新客户，系统抽风把别人的 `previous` 串进来了？

**标准处理原则**：

1. **不武断覆盖**：保留原始字段，不要擅自脑补正确答案。
2. **打标记特征（`is_contact_conflict`）**：建一个 `0/1` 列，把这 21 行标记为 `1`。如果系统数据错误与客户是否签约有相关性，模型自己能捕捉到；后续排查时也容易回溯。

---

### 四、总结：最终进模型的特征形态

做完这轮处理后，这组特征由原本的 3 列变成了清晰的 5 个特征：

| 最终特征名 | 数据来源与处理 | 作用 |
| --- | --- | --- |
| `has_previous_contact` | 从 `pdays` 提取二值（0/1） | 充当门控，区分新老客户 |
| `contact_gap` | `pdays` 将 -1 转为 0 | 衡量老客户的时间衰减 |
| `previous_log` | 对 `previous` 取 `log1p` | 压缩联系次数的长尾极大值（如联系了几十次的情况） |
| `poutcome` | 类别编码（如 One-Hot） | 保留上次成败反馈（success 的转化率通常极高） |
| `is_contact_conflict` | 逻辑冲突判断（0/1） | 标记脏数据行，防止噪声干扰主干规律 |
